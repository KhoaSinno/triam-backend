TriAm Phase 4.1 Training

Bản trực quan hóa kiến trúc in-app notification, durable outbox, Celery Beat và spaced review. Mục tiêu là hiểu để báo cáo và phản biện capstone, không chỉ thuộc tên công nghệ.

Postgres = source of truth Redis = broker Beat = đồng hồ Worker = người xử lý FE đọc user_notifications
Mental model Kiến trúc Bảng DB Luồng chạy Outbox state File map Debug Capstone Q&A

1. Mental Model

Database Postgres Lưu sự thật: settings, review schedule, outbox, inbox.
Queue Redis Chỉ vận chuyển task Celery. Không lưu business truth.
Scheduler Celery Beat Mỗi 60 giây bắn task scan_due vào queue maintenance.
Worker Celery Worker Consume queue maintenance/notification và cập nhật DB.
API FastAPI + Flutter FE gọi API để xem, đọc, cập nhật settings notification.
Câu nhớ nhanh: Postgres là nơi lưu sự thật. Redis chỉ là đường vận chuyển. Beat chỉ bắn task. Worker mới xử lý. FE đọc inbox từ DB qua API.

3. Bốn Bảng Quan Trọng

Bảng Vai trò Điểm cần nhớ
notification_settings Lưu cấu hình notification theo user. Timezone, reminder_time, quiet hours, daily_cap.
spaced_review_items Lưu lịch ôn tập 1/3/7/14/30 ngày. Unique theo user/chapter/mode/interval để không trùng.
notification_outbox Durable queue trong Postgres. Chống mất trạng thái, retry, lock, idempotency.
user_notifications Inbox cho FE hiển thị. Unique outbox_id để retry không tạo bong bóng trùng.

4.1 Chapter Ready

process_chapter()
-> run_tts_pipeline()
-> TTSChapterResult.review_text
-> mark_chapter_state_ready()
-> create_chapter_ready_learning_events()
   -> spaced_review_items
   -> content_ready outbox

Notification là phụ trợ. Nếu tạo notification lỗi, chapter vẫn READY.

4.2 Beat Scan

Celery Beat mỗi 60s
-> triam.notifications.scan_due
-> recover stale outbox
-> scan due reviews
-> scan reading plans
-> has_due_outbox()
-> enqueue deliver_due

`has_due_outbox()` giúp deliver cả outbox pending có sẵn.

4.3 Delivery

deliver_due_notifications_task()
-> claim_due_outbox(SKIP LOCKED)
-> deliver_one_notification()
-> create user_notifications
-> mark outbox sent

SKIP LOCKED giúp nhiều worker không xử lý trùng một row.

5. State Machine Của Outbox

pendingĐang chờ gửi
→
processingWorker đã claim
→
sentĐã tạo inbox
Khi lỗi tạm thời processing -> pending, set next_retry_at, tăng attempts.
Khi worker crash recover_stale_outbox() nhìn locked_at cũ và đưa về pending.

7. Debug Checklist

Beat có chạy không? Tìm log: Scheduler: Sending due task scan-due-notifications
Worker nghe đúng queue không? Log phải có queue maintenance và notification.
Scanner có tạo outbox không? Tìm log: Notification scan done | created=...
Outbox kẹt không? Kiểm tra status=processing và locked_at quá cũ.
Delivery có tạo inbox không? Kiểm tra bảng user_notifications.
FE có thấy không? Gọi GET /api/v1/notifications?limit=30.

8. Câu Trả Lời Capstone Mẫu

Vì sao cần outbox? Để notification delivery bền vững, retry được, không tạo trùng, và debug được khi worker crash.
Vì sao Postgres là source of truth? Vì Redis chỉ là broker. Business state phải sống qua restart, deploy, retry.
Nếu Beat chạy hai lần? Idempotency key unique ở DB ngăn tạo duplicate outbox.
Vì sao chưa push notification? Phase 4.1 ổn định outbox/in-app trước. Push cần Firebase, device token và mobile permissions.
Điểm phải nói rõ: Phase 4.1 muốn tự chạy đầy đủ khi deploy một runtime thì cần bật cả ENABLE_NOTIFICATION_WORKER=true và ENABLE_CELERY_BEAT=true. Chỉ một runtime được bật Beat.
